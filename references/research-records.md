# 记录与续查

在首次研究、继续下一批或接收业务反馈时阅读。目标是同一供方能续查、去重和纠错，不要求建立新系统。

## 最小保存方式

优先使用现有项目档案和台账。没有时，在用户工作目录按供方分别保存：一份可更新的供方档案、一份客户索引、每批一个Markdown交付文件。可用Markdown或已有JSON/表格，不强制再造数据库。不要保存到公共技能仓库、技能安装目录或另一个客户项目。

供方档案只记录会影响搜索的内容：

- 稳定供方标识、已核主体/品牌/域名、主营和实际承接实体。
- 主推业务、直接买方或渠道、目标场景与优先地区。
- 硬条件和软偏好分开；每项带来源、确认日期及未知状态。
- 用户认可/否定的客户样本及具体原因；不能把单家公司被拒推导成整个行业被拒。
- 现有客户、拒绝外联、暂停对象及适用范围。
- 批次编号、已交付客户编号、用户指定输出位置。

客户索引至少包括：稳定客户编号、供方标识、公司/品牌、规范化域名、已知关联主体、首次交付批次、适配状态、需求证据层级、联系结果、最近核查日期、排除/待核原因、对应批次文件。联系状态默认未联系；不要从“有邮箱”推导为已联系。

## 更新规则

1. 写入前先读取现有文件；保留用户编辑、既有编号和历史发送原文。
2. 同企业新来源或新型号更新原记录；若出现独立采购组织证据，可另编号并记录关联，不仅凭不同域名拆成多家。
3. 已结束的具体采购项目不再推荐为当前项目；不因此永久排除整个公司未来需求。当前批次用户拒绝则按用户的范围保留，不更名重新推荐。
4. 收到“太远/超规格/已合作/无人有需求”等反馈，先更新该客户，再判断是否改变供方筛选边界。只有用户确认或事实充分时才推广到以后批次。
5. 核查日期仅在实际重新读到相关来源后更新。交付日期可以更新，二者不混用。来源打不开时记录本次失败及原核查日期。
6. 先更新主记录，再同步本批阅读文件；核对公司编号、邮件收件人、数量和状态一致后宣布完成。输出被占用或保存失败时明确报告，不宣称已更新。
7. 更换供方时隔离私人信息；可复用通用搜索方法，不能复用另一公司的非公开名单或业绩。

## 完成门槛

- 身份、场景、硬条件、联系路径逐一可追溯，而非仅勾选“已核”。
- 正式数和候补数分列；不得把同一买方多个型号计为新增企业。
- 每封草稿使用该公司的事实、正确收件人和供方署名；未知内容用问题。
- 不以发送次数、搜索页数或自动回执代替实际需求；没有实际联系时转化率为不适用，不展示虚假0%效果结论。
- 无法核实的内容不补造，用户只需配合必要的内部判断。

## 维护时的情境检验

修改技能后，以以下情境检查决策是否仍正确；这些是检查案例，不是已实测的获客效果。

| 输入情境 | 应有行为 | 不可接受的行为 |
|---|---|---|
| 只给一个有多个同名主体的公司名 | 先查差异，再集中问城市/官网等最小区分信息 | 随机选一家并找满5个 |
| 软件服务商跨境交付，已有好客户样本 | 提炼业务场景、系统环境和服务边界 | 沿用包装行业的重量或运费阈值 |
| 5家制造商中1家重量未知，用户硬上限1000kg | 未知者候补，继续替换或报告正式4家 | 交付5家都称合格 |
| 用户要近期采购，只有2023年的公告 | 标历史，查当前项目；不足时说明缺额 | 把历史公告日期改成本次日期 |
| 官网只有商务表单，没有邮箱 | 核实表单用途，给可用文案与入口 | 猜测sales@域名或要求用户搜邮箱 |
| 用户说某企业是老客户 | 更新索引并从新增推荐排除 | 换一个品牌或产品重新算新客 |
| 查到扩产新闻但无采购信息 | 标近期触发线索，核适配与联系路径 | 宣称已确定正在采购我方产品 |
| 用户说资料够了，继续下一批 | 读取已确认档案、去重后继续 | 再问一遍公司和地区 |
| 用户希望只有MD、没有邮件草稿 | 只交付所需字段与证据 | 强制塞入邮件或另做总表 |
| 无网络或动态采购正文不可访问 | 限定结论，换可用来源或明确未核 | 只凭记忆生成已核验名单 |
